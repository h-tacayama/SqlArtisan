## [Unreleased]
### Docs
- `Sql.Trim(source, trimChar)`'s XML remark now states the SQL Server 2022+ floor (compatibility level 160) alongside its SQLite exclusion, matching what `docs/functions.md` already said and what the arity-2 matrix key already records. The floor was omitted because `XmlDocDialectParityTests` read *any* dialect named anywhere in a remark containing "Not supported by" as excluded, so naming SQL Server for its version floor also marked it unsupported and failed the parity gate. The parser now scopes the exclusion to its own clause — up to the first sentence/sub-clause boundary (a period that isn't part of a version number, or a semicolon) or em dash, the last kept defensively even though every "— use `<sibling>` there" aside in the corpus today names a function, not a dialect — and collapses wrapped whitespace first, since a doc comment can split a display name such as "SQL Server" across lines. Only the exclusion form is scoped; the positive-list form ("A, B, and C syntax.") still reads the whole remark, which is why the test's member list stays curated. (#469)
- Docs-audit corrections. The README's install commands now carry the `--prerelease` flag their own lead-in says is required (every published version is a prerelease, so the flagless commands resolved nothing). The README/comparison guard-rail item no longer claims the integration matrix "proves the SQL runs" — a few full-text-search entries' supported side cannot execute on the pinned container images, so it now says "verified against live engines," matching the AI-assistants guide. Every dialect-restricted entry in `docs/functions.md` that read as universally supported now carries a dialect note in the page's own style, each checked at the arity-specific matrix key and against the separate version-bound table — the Oracle-family conversion/date functions (`Nvl`, `Decode`, `ToChar`/`ToDate`/`ToNumber`/`ToTimestamp`, `AddMonths`, `MonthsBetween`, `Sysdate`/`Systimestamp`, date `Trunc`), the restricted character functions (`ConcatWs`, `CharLength`, `Instr`, `Left`/`Right`, `Lpad`/`Rpad`, `Ltrim`/`Rtrim` trim-set forms, `Length`, `Lengthb`/`Substrb`, the `REGEXP_*` family, `Substr`/`Substring`, `Trim`), `Extract`, `LastDay`, `Greatest`/`Least`, `CurrentDate`/`CurrentTime`, `PercentileCont`/`PercentileDisc`, and the SQLite 3.35+ math-function bounds (`Ceil`/`Ceiling`/`Exp`/`Floor`/`Ln`/`Log10`/`Mod`/`Power`/`Sign`/`Sqrt`, plus `Round`'s single-argument SQL Server gap and numeric `Trunc`'s single-argument SQLite support). Two needed more than the member-level row: `Trim`'s two-argument trim-set form carries its own SQL Server 2022 floor at the arity key rather than the member-level 2017 one, and numeric `Trunc` — which the analyzer's matrix deliberately leaves unentered, so nothing warns either way — runs on SQLite 3.35+ in its single-argument form, confirmed against the bundled engine and already asserted by the integration smoke catalog. `docs/analyzer.md` and `Sql.Trunc`'s XML remark, which both still described numeric `TRUNC` as Oracle/PostgreSQL, were corrected to match. The large-`IN`-list advice in `docs/expressions.md` now points at the shipped `Any(BindArray(...))` bound-array form instead of calling `= ANY` a raw idiom. (#468)
- Added a Hazard callouts rule to `.claude/rules/docs-style.md` distinguishing `[!WARNING]` (the same call's meaning silently changes with context — target dialect or schema drift — with no diagnostic on at least one such context) from `[!NOTE]` (a catchable hazard, a silent *absence* rather than a wrong value, or two correctly-named factories inviting mix-up) from a plain dialect-caveat bullet, with a hard length cap on each (`[!WARNING]` ≤10 lines, `[!NOTE]` ≤5, no table). Re-triaged `docs/functions.md` and `docs/expressions.md` against it: shrank the `Log`/`Stddev`/`Variance` `[!WARNING]` tables, demoted six pure cross-reference `[!NOTE]`s to plain prose, moved `DoublePipe`'s MySQL trap from a bare bullet to `[!NOTE]` (the analyzer catches it, so it's NOTE-tier, not risk-free), and promoted `docs/query-statements.md`'s `NATURAL JOIN` schema-drift caveat from a bare paragraph to `[!WARNING]`. The three forms are the whole taxonomy — a hazard never reaches for `[!IMPORTANT]`/`[!TIP]`/`[!CAUTION]`, which is how one would dodge both the severity question and the length cap at once. A new `DocsCalloutTests` gate (globbing every page under `docs/`) enforces the bounds mechanically going forward, applying the 10-line cap to every callout kind so no tag choice bypasses it. (#458)

### Added
- `Sql.RegexpInstr(source, pattern, ...)` for `REGEXP_INSTR` — the one member of the `REGEXP_*` family (`RegexpCount`/`RegexpReplace`/`RegexpSubstr`) that was still missing. Mirrors `RegexpSubstr`'s progressive overload ladder (`position`/`occurrence`/match options/`subPatternPos`), plus its own `returnOption` argument (0 for the match's first-character position, 1 for the position following it). Runs on MySQL, Oracle, and PostgreSQL (15+, vendor-verified alongside its siblings); the 7-argument overload carrying `subPatternPos` is Oracle/PostgreSQL only — MySQL's `REGEXP_INSTR` tops out at 6 arguments, with no `subexpr`. See [Functions: Character Functions](https://github.com/h-tacayama/SqlArtisan/blob/main/docs/functions.md#character-functions). (#446)
- `Sql.Substring(source, position, length)` for SQL Server's `SUBSTRING` — the only substring spelling that dialect has, since it has no `SUBSTR`. Unlike `Substr`, `length` is required (SQL Server's grammar has no 2-argument form). `Substring` also runs on MySQL, PostgreSQL, and SQLite (3.34+, vendor-verified: SQLite registered `SUBSTRING` as a second name for `substr()` there); Oracle has no `SUBSTRING` (`ORA-00904`) — use `Substr` there instead. See [Functions: Character Functions](https://github.com/h-tacayama/SqlArtisan/blob/main/docs/functions.md#character-functions). (#445)
- `Sql.ConcatWs(sep, a, b, ...)`, `Sql.CharLength(str)`, `Sql.Left(str, n)`/`Sql.Right(str, n)`, `Sql.Position(substr, str)`, and `Sql.Strpos(str, substr)` — six ubiquitous string helpers `CharacterFunction/` was missing entirely. `ConcatWs` requires at least two values (SQL Server's own arity floor for `CONCAT_WS`) and carries version bounds for SQL Server 2017+ and SQLite 3.44+ (both vendor-verified); it has no Oracle spelling (`ORA-00904`). `Position(substr, str)` and `Strpos(str, substr)` are two separate factories, not one dialect-switched call: MySQL/PostgreSQL's `POSITION(substr IN str)` and PostgreSQL's own `STRPOS(str, substr)` differ in both keyword-vs-function-call syntax and argument order — a construct difference, not a token swap — and neither runs on Oracle, SQLite, or SQL Server, which spell this `INSTR`/`CHARINDEX` instead. `CharLength` is MySQL/PostgreSQL only; `Left`/`Right` add SQL Server. See [Functions: Character Functions](https://github.com/h-tacayama/SqlArtisan/blob/main/docs/functions.md#character-functions). (#444)
- `Sql.Ifnull(expr, alt)`/`Sql.Isnull(expr, alt)` and `Sql.If(condition, then, else)`/`Sql.Iif(condition, then, else)` — MySQL/SQLite's `IFNULL`, SQL Server's `ISNULL`, MySQL's `IF`, and SQLite/SQL Server's `IIF`, the dialect-faithful siblings `Coalesce`/`Nvl`/`Decode` already establish as the house pattern for conditional NULL-handling and branching. `Isnull` is deliberately not to be confused with the pre-existing `expr.IsNull` property (`IS NULL`, a predicate) — same letters, different capitalization, different construct — and `If` is deliberately not `ConditionIf` (a C#-side helper that emits no SQL); both pairs cross-reference explicitly in their XML docs and in `docs/functions.md`. `If`/`Iif` take a `SqlCondition` first argument (mirroring `Sql.When(SqlCondition)`) and throw `ArgumentException` for an empty condition, following the project's `WHERE`/`CASE WHEN` empty-condition policy. A harness probe found SQLite also accepts `IF(...)` as a second name for `IIF`, added in SQLite 3.48 (confirmed against the `sqlite/sqlite` source mirror), so `If` carries a SQLite version bound and `SQLA0101` flags it below 3.48. See [Functions: Conversion Functions](https://github.com/h-tacayama/SqlArtisan/blob/main/docs/functions.md#conversion-functions). (#443)
- `Sql.StddevPop(x)`/`Sql.StddevSamp(x)` and `Sql.VarPop(x)`/`Sql.VarSamp(x)` — `STDDEV_POP`/`STDDEV_SAMP`/`VAR_POP`/`VAR_SAMP`, universal on MySQL/Oracle/PostgreSQL with no SQLite spelling; plus `Sql.Stddev(x)`/`Sql.Variance(x)`, those three dialects' short-form aliases, and SQL Server's own distinct tokens `Sql.Stdev(x)`/`Sql.Stdevp(x)`/`Sql.Var(x)`/`Sql.Varp(x)` (no double-D there). `Stddev`/`Variance` ship despite computing a different statistic per dialect — MySQL's is the population form, Oracle's and PostgreSQL's the sample form — the same `Log(x)`-style silent-meaning-change #440/#441 settled: an accepted, opinion-free spelling stays available with the hazard carried in `docs/functions.md`'s warning table rather than withheld from the API, since all three engines run it and return a (different) number, so `SQLA0100` cannot catch the mismatch. `StddevPop`/`StddevSamp`/`VarPop`/`VarSamp` avoid it entirely and are the recommended spelling when a query must mean the same thing everywhere it runs. All ten derive from the existing `UnfilteredAggregateFunction` base, so `.Over(...)`/`.Filter(...)` compose for free. `DISTINCT` overloads and MySQL's `STD()` alias are intentionally out of scope. See [Functions: Aggregate](https://github.com/h-tacayama/SqlArtisan/blob/main/docs/functions.md#aggregate-functions). (#442)
- `Sql.Exp(x)`, `Sql.Ln(x)`, `Sql.Log(x)`, `Sql.Log(base, x)`, and `Sql.Log10(x)` — the exponential and logarithmic functions, which `NumericFunction/` had none of. Only `EXP` means the same thing on all five dialects: `LN` has no T-SQL spelling (SQL Server's natural logarithm *is* its `LOG(x)`), `LOG10` has no Oracle one, and `LOG` itself silently changes meaning per dialect in **both** its forms — the base of `LOG(x)`, and the argument order of `LOG(base, x)`, which T-SQL reverses. Only Oracle errors on the mismatch; every other dialect runs and returns a number. Both `LOG` forms ship rather than being withheld, as the design-decision issue considered: `LOG(x)` is SQL Server's only natural logarithm, so omitting it would leave a dialect unable to express the query at all — the same failure mode that reversed `COUNT(*)`'s omission ("opinions live in docs and the analyzer, never in API holes"). `SQLA0100` covers what's provable instead — `Log(x)`/`Log10(x)` on Oracle, `Ln(x)`/`Log(base, x)` on SQL Server — and `Log10` carries a PostgreSQL 12 version bound. See [Functions: Numeric](https://github.com/h-tacayama/SqlArtisan/blob/main/docs/functions.md#numeric-functions). (#440, #441)
- `Sql.Date(timevalue)` / `Sql.Date(timevalue, modifier, ...)`, `Sql.Datetime(timevalue, ...)`, `Sql.Julianday(timevalue, ...)`, and `Sql.Strftime(format, timevalue, ...)` — SQLite's `DATE`/`DATETIME`/`JULIANDAY`/`STRFTIME` functions. Before this, SQLite's only date/time factories were `CurrentDate`/`CurrentTime`/`CurrentTimestamp`: no `Extract`, no truncation, no arithmetic. Trailing modifier strings (e.g. `"+30 days"`, `"start of month"`) are plain `object` arguments bound as parameters, not a fixed enum: SQLite's modifier grammar is open-ended (arbitrary offsets), so no fixed type could cover it faithfully. `Date` splits into a 1-argument overload and a 3+-argument overload (a leading required modifier ahead of the `params` tail) because the bare `DATE(timevalue)` form is also valid on MySQL (extracts the date part) and PostgreSQL (casts to `date`), while the modifier form is SQLite-only — the same overload-split-by-arity shape `Concat` uses. `Datetime`/`Julianday`/`Strftime` have no equivalent on any other supported dialect. All four are unconditionally available on the project's bundled SQLite build — unlike SQLite's math functions, its date/time functions are core, confirmed by an in-process harness probe against the pinned `SQLitePCLRaw.bundle_e_sqlite3` 3.0.3 (engine 3.50.4), including binding the modifier strings themselves as parameters rather than inlining them. (#439)
- `Sql.Timestampadd(unit, number, dateTime)` and `Sql.Timestampdiff(unit, startDate, endDate)` — MySQL's `TIMESTAMPADD`/`TIMESTAMPDIFF` functions, independent of `DATE_ADD`/`DATE_SUB`/`INTERVAL`: `unit` is a bare keyword (e.g. `TIMESTAMPADD(DAY, ?0, created_at)`), not an `Interval(...)` expression. Both reuse the existing `DateTimePart` enum — its nine simple units (`Microsecond` through `Year`) already cover MySQL's vocabulary for these two functions, so no new member was needed. `SQLA0104` gained its own list for the pair, narrower than `Extract`'s: `Timestampadd`/`Timestampdiff` reject the compound units (`DAY_HOUR`, `YEAR_MONTH`, ...) that `Extract`/`Interval` accept. `Timestampdiff`'s argument order (`startDate` then `endDate`, i.e. `endDate - startDate`) is the reverse of MySQL's own two-argument `DATEDIFF(expr1, expr2)`, noted on the factory. (#438)
- `Sql.DateAdd(date, interval)` and `Sql.DateSub(date, interval)` — MySQL's `DATE_ADD`/`DATE_SUB` functions, taking their shift amount from an `Interval(...)` or `IntervalLiteral(...)` expression (e.g. `DateAdd(u.CreatedAt, Interval(30, DateTimePart.Day))` → `DATE_ADD(created_at, INTERVAL ?0 DAY)`). `DateAdd` is visually one capital letter away from the pre-existing `Dateadd` (SQL Server's `DATEADD`, a different argument shape entirely) — both factories' XML docs cross-reference each other and name their dialect explicitly. The existing `SQLA0102` context rule for `Interval(...)`/2-argument `IntervalLiteral(...)` outside a `+`/`-` date-arithmetic expression now also accepts either as `DateAdd`/`DateSub`'s second argument. (#437)
- A `SQLA0104` analyzer warning for a literal `DateTimePart` argument to `Extract`/`Datepart`/`Dateadd`/`Datediff`/`DateTrunc`/`Datetrunc`/`Interval` that the target dialect's own grammar doesn't accept for that function — e.g. `Extract(DateTimePart.Epoch, x)` targeting Oracle, where `EPOCH` is a PostgreSQL-only field. A finer grain than `SQLA0100`'s whole-construct check: these seven functions share one 42-member `DateTimePart` enum whose valid fields overlap only partially across engines, so the construct itself can pass while the argument value doesn't. Stays silent for a non-constant argument, a (function, dialect) pair this rule has no list for, or a dialect `SQLA0100`/`SQLA0101` already flags unsupported (avoiding a double report). See [Datepart validity](https://github.com/h-tacayama/SqlArtisan/blob/main/docs/analyzer.md#datepart-validity-sqla0104). (#449)
- `Sql.Numtoyminterval(n, unit)` and `Sql.Numtodsinterval(n, unit)` — Oracle's `NUMTOYMINTERVAL`/`NUMTODSINTERVAL` functions, the bindable-quantity counterparts to `IntervalLiteral`'s Oracle field and field-range forms: an Oracle interval literal never binds its value, so these give the quantity its own bind-parameter path. `n` binds as a parameter; `unit` renders as a quoted inline literal, restricted to `DateTimePart.Year`/`Month` (`Numtoyminterval`) or `Day`/`Hour`/`Minute`/`Second` (`Numtodsinterval`) — the exact sets each Oracle function accepts, since no other engine has either function. Any other unit throws `ArgumentException` eagerly. (#448)
- `Sql.Interval(quantity, unit)` and `Sql.IntervalLiteral(...)` — `INTERVAL` date-shift expressions for MySQL, Oracle, and PostgreSQL, closing the gap where `WHERE created_at >= NOW() - INTERVAL 30 DAY` had no spelling on any of them. `Interval(object, DateTimePart)` binds its quantity as a parameter (MySQL's unquoted `INTERVAL n unit`); `IntervalLiteral(string)` / `IntervalLiteral(string, IntervalField)` / `IntervalLiteral(string, IntervalField, IntervalField)` emit their value inline as a quoted literal (PostgreSQL's bare-text form, and Oracle/PostgreSQL's field and field-range forms — e.g. `IntervalLiteral("123-11", Year(3), ToMonth)` for `INTERVAL '123-11' YEAR(3) TO MONTH`). An `IntervalField` comes from `Year()` / `Month()` / `Day()` / `Hour()` / `Minute()` / `Second()`, or — for a range's trailing field — `ToMonth` / `ToHour` / `ToMinute` / `ToSecond()`. Oracle's precision (0-9) rides on `Year` / `Month` / `Day` / `Hour` / `Minute` as a sole or leading field, and on `ToSecond` as a trailing one — the only trailing field that may carry it, since that position is Oracle's fractional-seconds count. `Second()` takes none: Oracle reads a standalone `SECOND(n)` as the leading count, so spell that form `ToSecond(n)` as a sole field. Composing a range outside the seven pairings Oracle's grammar allows, or putting a precision anywhere else on the trailing side, throws `ArgumentException` eagerly. Combine either factory with the existing `+`/`-` operators for date arithmetic. See [Expressions: Interval Expressions](https://github.com/h-tacayama/SqlArtisan/blob/main/docs/expressions.md#interval-expressions). (#436)
- A `SQLA0102` context rule for MySQL: `Interval(...)` / the 2-argument `IntervalLiteral(...)` used outside a `+`/`-` date-arithmetic expression now warns — MySQL's `INTERVAL` keyword has no standalone value, so `Select(Interval(30, DateTimePart.Day))` parses on no engine even though the construct itself is MySQL-supported. Follows the existing context-rule contract: it warns only where the bare-argument position is provable from the expression itself, so a value held in a variable and used correctly later stays silent. See [Context rules (SQLA0102)](https://github.com/h-tacayama/SqlArtisan/blob/main/docs/analyzer.md#context-rules-sqla0102). (#436)
- `sqlartisan_syntax_<dbms>` — one `.editorconfig` key per DBMS (`= <version>` or `= any`), for a project that must run on more than one engine at once: an ISV shipping against several customer-chosen databases, a migration in progress, or a "standard SQL only" requirement (name all five). Every rule now evaluates against the whole configured set instead of a single target — `SQLA0100` joins every failing dialect's name into one diagnostic, `SQLA0101`/`SQLA0103` report one diagnostic per failing dialect since their message carries a per-dialect value that can't join, and a construct can fail two different ways across the set at once (both reported). A `sqlartisan_construct_*` override is resolved once per usage regardless of how many dialects are configured, exactly as before. `none` in a narrower `.editorconfig` scope excludes a dialect a broader scope or the MSBuild property named; a key set to nothing at all reads as unset, not as `none`, so the `<SqlArtisanSyntax*>` properties the package declares leave a project that sets none of them exactly as silent as before. See [Checking a set of dialects at once](https://github.com/h-tacayama/SqlArtisan/blob/main/docs/analyzer.md#checking-a-set-of-dialects-at-once). (#432)
- Two `SQLA0102` context rules for SQL Server. `PercentileCont(...)` / `PercentileDisc(...)` left in the plain `WithinGroup(...)` form now warn — SQL Server exposes both percentiles only as window functions, so the form Oracle and PostgreSQL accept has no spelling there; chain `.Over()` after `.WithinGroup(...)`. `Inserted(...)` / `Deleted(...)` used outside `Output(...)` now warn too — the `OUTPUT` clause is what binds those pseudo-tables, so a reference elsewhere resolves against no table. Both follow the existing context-rule contract: they warn only where the position is provable from the expression itself, so an expression held in a variable stays silent. (#400)

### Changed
- **Breaking:** renumbered the analyzer diagnostic IDs into per-category bands, and split two new categories out of `SqlArtisan.Dialect`. Each ID now sits in a numbered range that *is* its category — `SQLA0001`–`0099` `SqlArtisan.Configuration`, `SQLA0100`–`0199` `SqlArtisan.Dialect`, `SQLA0200`–`0299` `SqlArtisan.Schema`, `SQLA0300`–`0399` `SqlArtisan.Validity` — so a family can gain a rule without renumbering and a bulk-severity setting reaches one family only. What each rule reports, its severity, and its default-enabled state are all unchanged; only the ID and the category move. A `dotnet_diagnostic.SQLA00xx.severity` line, `#pragma warning disable`, `[SuppressMessage]`, or `NoWarn` entry written against 0.8.0-beta.1 now targets a different diagnostic or none at all — remap with the table below. `SQLA0001` keeps its number and moves to `SqlArtisan.Configuration`; `SQLA0005` becomes `SQLA0300` in the new `SqlArtisan.Validity` category. The flat sequence had run out of room in the dialect range and had already forced one mid-flight move (`SQLA0003` → `SQLA0006`, #326/#349); 0.x is the last window in which this is fixable. See the [rules table](https://github.com/h-tacayama/SqlArtisan/blob/main/docs/analyzer.md#rules). (#433)

  | Old | New | Rule |
  |---|---|---|
  | `SQLA0001` | `SQLA0001` | Invalid analyzer configuration |
  | `SQLA0002` | `SQLA0100` | Construct unsupported on the target dialect |
  | `SQLA0003` | `SQLA0101` | Construct version-bound above the declared version |
  | `SQLA0004` | `SQLA0102` | Construct restricted in this position |
  | `SQLA0006` | `SQLA0103` | Identifier exceeds the dialect's length limit |
  | `SQLA0007` | `SQLA0200` | Constant NULL predicate |
  | `SQLA0008` | `SQLA0201` | `NOT IN` over a nullable subquery column |
  | `SQLA0009` | `SQLA0202` | `INSERT` omits a required column |
  | `SQLA0010` | `SQLA0203` | `Count(col)` on a nullable column |
  | `SQLA0011` | `SQLA0204` | Filter makes an index unusable |
  | `SQLA0012` | `SQLA0205` | Column compared across type categories |
  | `SQLA0005` | `SQLA0300` | Correlated UPDATE/DELETE target not aliased |

  Entries in released sections below keep the IDs those releases actually shipped; their links into `docs/analyzer.md` were repointed to the renamed headings, so they still reach the section that documents the rule today.
- **Breaking:** `sqlartisan_target_dbms` / `sqlartisan_target_version` are deprecated in favor of `sqlartisan_syntax_<dbms>` and now report `SQLA0002`, a new `SqlArtisan.Configuration` warning, once per compilation whenever either legacy key resolves with no `sqlartisan_syntax_*` key present — even when the pair is used alone and resolves perfectly correctly. A project with `TreatWarningsAsErrors` fails to build on upgrade with no config change of its own; migrate with `sqlartisan_target_dbms = postgresql` + `sqlartisan_target_version = 16` → `sqlartisan_syntax_postgresql = 16`. If you cannot migrate immediately, suppress `SQLA0002` specifically — **not** `SQLA0001` and **not** the `SqlArtisan.Configuration` category setting, either of which would also silence real configuration-error detection — via a global analyzer config (`.globalconfig` with `is_global = true`) or `<NoWarn>SQLA0002</NoWarn>`; a file-scoped `.editorconfig` `dotnet_diagnostic.SQLA0002.severity` line does not reach it, since it carries no file location. The legacy pair still resolves exactly as before wherever it governs — that is, wherever no `sqlartisan_syntax_*` key is present. `SQLA0001` also widens from reporting only an unrecognized value to reporting any SqlArtisan analyzer configuration problem: an unrecognized `sqlartisan_syntax_*` key name, a `sqlartisan_syntax_*` family that resolves to no dialect at all, and the legacy pair coexisting with a family that doesn't itself name the legacy pair's DBMS (which drops it rather than merging it in; a family that does name that DBMS — mid-migration, with the old line not yet deleted — drops nothing, so no coexistence report fires). See [Migrating from the legacy target key](https://github.com/h-tacayama/SqlArtisan/blob/main/docs/analyzer.md#migrating-from-the-legacy-target-key). (#432)
- `Sql.Coalesce(...)`, `Sql.Concat(...)`, `Sql.Grouping(...)`, and `Sql.GroupingId(...)` allocate one array per construction instead of two — they previously resolved their `params` tail into its own array and then merged it with the leading arguments. Construction allocates one array fewer, so the saving starts at 24 B for the shortest call and grows with the `params` tail — a five-argument `Concat` drops 216 B, a nineteen-argument one over 400 B. The emitted SQL and every null-argument message are unchanged. (#413)
- **Breaking:** `SqlArtisan.Internal.DeleteClause` and `SqlArtisan.Internal.EqualityCondition` are now `internal`, matching the twins they sat beside — `UpdateClause` and `InequalityCondition`. No public signature ever returned or accepted either, so neither could reach your code on its own: `DeleteClause`'s constructor was already `internal`, and `EqualityCondition` is only ever produced by `==`, which returns the public `EqualityBasedCondition` a `SET` list is written in terms of. `EqualityCondition`'s primary constructor was reachable, though, so a direct `new EqualityCondition(a, b)` no longer compiles — write `a == b` instead, which is what every assignment position already takes. (#410)
- **Breaking:** `InnerJoin(...)` / `LeftJoin(...)` / `RightJoin(...)` / `FullJoin(...)` / `JoinLateral(...)` no longer expose `Build(...)` or `ForUpdate(...)` before `.On(...)` / `.Using(...)` supplies the join predicate. Omitting it is a syntax error on PostgreSQL and MySQL (except `InnerJoin`/`JoinLateral`, which MySQL silently reads as an unlabeled `CROSS JOIN`) and on SQLite for every one of the five — all read as the same unlabeled `CROSS JOIN`, a spelling the library already exposes under its own name (`CrossJoin`). `ISelectBuilderJoin` no longer extends `ISqlBuilder`/`IForUpdate`, so the omission is now a compile error on every dialect; a chain that already supplies `.On(...)`/`.Using(...)` is unaffected. Binary-breaking — rebuild against this version. (#400)

### Fixed
- `SQLA0100` now flags `Sql.RegexpSubstr`'s 6-argument `subPatternPos` overload on MySQL. That overload's XML docs inherited the 2-argument member's "MySQL, Oracle, and PostgreSQL (15+)" claim, and the `DialectMatrix` carried only a member-wide entry, so the analyzer stayed silent on a statement MySQL's `REGEXP_SUBSTR` — which has no `subexpr` argument — cannot parse. If your code already calls this overload targeting MySQL, it will start reporting `SQLA0100`; the call was never valid there. (#463)
- `SQLA0101` did not flag `Ceil`, `Ceiling`, `Floor`, `Mod`, `Power`, `Sign`, or `Sqrt` below SQLite 3.35, though the dialect matrix's own comment already named that floor — all seven are `SQLITE_ENABLE_MATH_FUNCTIONS` extension functions, absent before 3.35, so a project declaring `sqlartisan_syntax_sqlite` below 3.35 got analyzer silence and a runtime `no such function` error instead of a warning. All seven now carry the bound, as do the five functions added above. (#440)
- A declared engine version with non-letter junk after the digits — `sqlartisan_syntax_postgresql = 14!!`, `sqlartisan_target_version = 16 or so` — was silently read as its leading digits instead of being rejected, so the value check stayed quiet and the junk spelling even surfaced verbatim in the `SQLA0101` message. The documented format ignores only a trailing *letter* run (`23ai`, `21c`); anything else after the digits is now an unrecognized value, reported as `SQLA0001`. (#432)
- The analyzer reported `DeleteFrom(t).Using(...)` (plain PostgreSQL `DELETE ... USING`, no version requirement) as version-bound below PostgreSQL 15 — a false positive borrowed from `MergeInto(...).Using(...)`'s MERGE-specific bound, since both overloads share one dialect-matrix key. `Using`'s key no longer carries a version bound; `MergeInto`'s own bound still flags a `MERGE` statement below PostgreSQL 15. (#432)

The derived table is named by a `DerivedTableBase` handle — subclass it for typed `DbColumn` members, or use the inline `DerivedTable` and read columns with `Column(...)`. `Build(Dbms)` emits faithfully and never rewrites one form into the other; availability is left to the database and the analyzer. (#122)
- Added support for the GROUP BY grouping extensions `Rollup(...)`, `Cube(...)`, and `GroupingSets(...)`. `Group(...)` forms a composite grouping element — a multi-column set inside `GroupingSets(...)`, or a parenthesized composite column inside `Rollup(...)` / `Cube(...)` (e.g. `Rollup(Group(a, b), c)` → `ROLLUP((a, b), c)`) — with `Group()` being the grand total; a single-column `Group(x)` renders bare as `x`. All three always emit their standard function forms (`ROLLUP(...)` / `CUBE(...)` / `GROUPING SETS(...)`) on every dialect. `Build(Dbms)` emits faithfully and does not gate on DBMS availability — an unsupported combination (e.g. `Cube` or the function-form `Rollup(...)` on MySQL, any extension on SQLite) is emitted as written for the database/analyzer to flag, not thrown. (#121)
- Added MySQL's `WITH ROLLUP` GROUP BY suffix as a dedicated builder step: chain `.WithRollup()` onto `GroupBy(...)` (e.g. `GroupBy(a, b).WithRollup()` → `GROUP BY a, b WITH ROLLUP`). This is MySQL's grouping syntax; other dialects use the standard `Sql.Rollup(...)` function form. (#121)
- Added support for the `ESCAPE` clause on `LIKE` / `NOT LIKE`: chain `.Escape(escapeChar)` onto a `Like(...)` / `NotLike(...)` condition (e.g. `Like("100%_off").Escape('!')`) to match wildcards (`%`, `_`) literally. The escape character is emitted as an inline string literal (single-quote- and, on MySQL, backslash-escaped) rather than a bind parameter, since MySQL rejects a parameter marker after `ESCAPE`; the clause is valid identically across all dialects. (#123)
- Documented the entire public API with XML doc comments and enabled `GenerateDocumentationFile`, so the published packages now ship IntelliSense — summaries, parameters, the emitted-SQL form, and dialect notes — for every public `Sql.*` factory, fluent builder step, and type (the internal function-node classes remain implementation detail and are not documented). (#120)
- Documented the public `SqlArtisan.Dapper` surface and enabled `GenerateDocumentationFile` for that package, so its `IDbConnection` extensions (`Execute` / `Query` / `QuerySingle` / `QueryFirst` / `ExecuteScalar` / `QueryMultiple` / `ExecuteReader` and their async variants) and `ToDynamicParameters` now ship IntelliSense. (#133)

### Changed
- **[BREAKING CHANGE]** Renamed the CTE schema base class `CteSchemaBase` to `CteBase` (and named the new derived-table base `DerivedTableBase`, not `DerivedTableSchemaBase`), dropping the `Schema` term that read inconsistently with `DbTableBase` and invited confusion with a database schema. CTE subclasses update only the base type name (e.g. `class MyCte : CteSchemaBase` → `: CteBase`); emitted SQL is unchanged. (#122)
- Reworked the benchmark suite into a fair builder comparison (every entrant emits SQL plus bind parameters for the same query), added linq2db and a labeled EF Core reference, and refreshed the README Performance section. (#79)

### Fixed
- CTE and derived-table names are now alias-quoted at their definition (`WITH "cte" AS ...`, `... ) "x"`) and at every reference (`FROM "cte"`, `... JOIN ... "x"`), consistent with the already-quoted column references through their handles (`"cte".col` / `"x".col`). Previously the name was emitted bare, so on Oracle it case-folded (`cte` → `CTE`) while the quoted column reference stayed lowercase, yielding an unresolvable qualifier (ORA-00904) — most visibly for `CROSS APPLY` / `OUTER APPLY`, whose primary target is Oracle. Emitted SQL for CTEs changes accordingly (the name is now quoted). (#122)
- `GroupBy(...)` with a `null` grouping item now throws a clear `ArgumentNullException` instead of a `NullReferenceException`. (#121)
- `Rollup(...)`, `Cube(...)`, and `GroupingSets(...)` with a `null` trailing `params` array (e.g. `Rollup(a, null)`) now throw a clear `ArgumentNullException` instead of a `NullReferenceException`. (#121)
- **SqlArtisan.TableClassGen**: generated class/property names are now sanitized into valid C# identifiers — a column name starting with a digit, containing Oracle's `$` / `#`, or consisting only of separators previously produced uncompilable code. (#141)

### Fixed
- Aliased DML now renders dialect-correctly. A table alias in `InsertInto` / `Update` / `DeleteFrom` is introduced with `AS` (PostgreSQL/SQLite/MySQL/SQL Server) or a bare space (Oracle), and target columns — the INSERT column list, the `ON CONFLICT` target, and `SET` / `DO UPDATE SET` left sides — are emitted unqualified. This makes the PostgreSQL `INSERT INTO t AS x ... ON CONFLICT ... DO UPDATE ... WHERE x.col` UPSERT idiom and aliased `UPDATE` / `DELETE` executable; previously they reused the SELECT-context aliasing (`t "x"` + `"x".col`) and produced invalid SQL. Aliasing the DML target itself remains engine-dependent and is not validated: SQL Server's structural single-table aliased `DELETE` / `UPDATE` (`DELETE x FROM t AS x` / `UPDATE x SET ... FROM t AS x`) is intentionally not emitted, and some engines reject an aliased INSERT target (e.g. MySQL has no alias slot in `INSERT INTO`). Since a single-table DML never requires an alias, omit it on those engines — `DeleteFrom(t).Where(...)` already renders valid unaliased SQL. (#96)
- `ORDER BY` can now follow `HAVING`: `GroupBy(...).Having(...).OrderBy(...)` previously did not compile, making `GROUP BY ... HAVING ... ORDER BY ...` inexpressible. (#111)
