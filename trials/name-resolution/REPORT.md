# 検証 3: 性質の違う型「名前の解決」 — 報告

価値の読み取りの試し（`trials/value-reading/REPORT.md`）と同じ手順を、別の型に当てた記録。
型の定義: **C# が名指した列・表を、どこかのエンジンが別の列・別のスコープに結びつける**
（静かに別の値を読む、または大きく失敗する）。issue も PR も作らず、不具合は直していない。

  うち 3 つは、記録（DialectMatrix 2 か所と `docs/query-statements.md` 1 か所）を模型が

- **静かな誤りが出るのに、どの記録も決めていないもの: 7 種類**（§ 6 の問い）。重い順に並べる。
  1. 内側のブロックの関係が外側と同じ別名を持つと、外側を指す修飾列が内側に結びつく（N3）。
     8 レーンすべてで静かに起きる。`DELETE` では消す行が変わる。SQLite と SQL Server では、
     大文字と小文字だけが違う別名（`"x"` と `"X"`）でも起きる。
  2. 基表と同じ名前の CTE を置くと、文の中のその表への参照が全部 CTE を読む（N12）。MySQL・
     PostgreSQL・SQLite・SQL Server で静かに起きる。Oracle では起きない。CTE 名は小文字の
     引用付きで描かれ、表名は大文字に畳まれるので、名前が一致しないため。
  3. MySQL の upsert の副問い合わせで表に `new` という別名を付けると、`Excluded(...)` がその
     表を読む（N13）。
  4. 複合問い合わせの最上位の枝で、別の枝にしか載っていない表の裸の列が、その枝の同名の列に
     結びつく（N10）。8 レーンすべて。
  5. `Using(col)` の列の持ち主が、結合する 2 つの表のどちらでもなくても通る（N6）。MySQL・
     PostgreSQL・SQLite で静かに起きる。
  6. `DistinctOn(g)` の裸の列が、同名の選択別名に結びつく（N1 のうち DISTINCT ON）。
     PostgreSQL。
  7. MySQL の `VALUES` の中の列参照が、同じ行の先に書いた列を読む（N14）。

## 10. この型で分かったこと（手法の評価への材料）

- **模型の中にあっても、Example がなければ見つからない。** これは試し 1 と同じだった。
  - レビューの High 1 は、SELECT の形では模型に Example があり、エンジンで静かな誤りとして
    見えていた（PRED-Q-SAMEALIAS）。
  - DML の形（DELETE で行が消える）は、セルはあっても Example がなかった。
- **模型の外は、レビューが見つけた。**
  - 同名の CTE（N12）
  - 大文字小文字だけ違う別名
  - MySQL の `new`

  名前の解決は「何が名前を持ち込むか」の軸が開いていて、表・別名・CTE・疑似行・row alias と
  後から増えた。試し 1 の値の種類より閉じにくい。
- **問いのセルが多い（24%）。** 記録は、守るために guard を入れた形（#677・#674）を細かく
  決めている。一方で、guard のない衝突（同じ別名・同名の CTE・USING）にはほとんど触れて
  いない。このため、模型を記録に合わせると問いが多くなる。
- **生成器で Example を作れなかった。** 文の形が位置ごとに違うので、Example を手で書いた。
  その結果、対ごとの網羅は 38% にとどまった。
- **Stryker は型の内側の穴を指した。** 回 2 では、試しの Example は型の内側の誤りを 1 つも
  捕まえなかった。生き残りを見て足した 5 本で 10 個を捕まえ、そのうち 1 本（UPD-B-BRANCH-LISTED）は
  後追いで捕まえられなかった #745 の形でもあった。
- **型の外の記録（行列・文書の注記）を引く段が要る。** 外れ 4 種のうち 3 種がその見落としだった。
