# 価値の読み取りの型: 族ごとの「意図した結果」の案

§ 14 の決定（型の境界はエンジン定義の読み方まで含める、期待は記録に合わせる）を受けて、記録が
決めていない族、または記録とエンジンが食い違う族ごとに、意図した結果の案を並べる。決めるのは
依頼者で、この文書は何も決めていない。issue は作っていない。

## 共通の物差し

族ごとの選択肢は、次の 6 つの置き場のどれかになる。それぞれの置き場を許す記録を右に挙げる。

| 置き場 | 使える条件（記録） |
|---|---|
| **G**: `Build(Dbms)` が拒む | ADR 0011 の bounded exception。ある方言では有効で、解析器から見えず（値の水準）、かつ対象の方言に正しい書き方がない |
| **A104**: SQLA0104 の行 | ADR 0022。対象の方言が拒む、または**別の意味で実行する**（#684 で広げた）定数の引数の値。前例は 6 つ。そのうち 2 つ（負の `Round` の桁、`+` の隣の文字列）は #742 で足した |
| **A205**: SQLA0205 の拡張 | ADR 0010 の Tier 2（スキーマを使う分類上の判断）。列の型の区分（`DbTypeCategory`）がテーブルクラスに載っているときだけ報告する。区分には幅（整数か小数か）がない。これは意図した設計で、`DbTypeCategory.cs` のコメントに理由がある |
| **D**: 文書の注記 | ADR 0020。結果の意味を書いてよいのは、生きたエンジンでの双子の試験（twin）が支えるときだけ。それ以外はエンジンの文書へのリンクにとどめる（docs-style「Result semantics are the engine's」） |
| **E**: エンジンに任せる（何もしない。決定だけ記録する） | ADR 0003 の Consequences は、丸め方・切り捨て・型の制限を「どの方式でも範囲外、文書で扱う」とする |
| **R**: 記録を直す | 記録に書かれた事実が誤っているとき |

推奨は「静かな誤りを、決定的な層で、誤検知なしに止められるか」（ADR 0010）を軸に選んだ。

---

## 族 1: MySQL で整数の `Bind(n)` をキーに置くと列の位置になる（F1、Q4）

- **事実**（MySQL 8.0、MySqlConnector 2.4.0）
  - 文の ORDER BY・GROUP BY・複合の末尾 ORDER BY では、列 n の位置として読まれる（静か）。
  - `OVER`・`PARTITION BY`・`GROUP_CONCAT` の ORDER BY では大きな失敗。
  - ほかの 7 レーンでは、定数になるか大きな失敗。
- **記録**: guards § bound-value は「`Bind(value)` keeps a deliberate constant writable」と約束する。
  `OrderByClause` の例外メッセージも `Bind` を勧める。
- **原因**: ドライバーがパラメーターを文字として埋め込んでいると見ている。確かめていない。

| 案 | 中身 |
|---|---|
| 1a（G） | `Build(MySql)` で、整数型の `Bind` を文の ORDER BY・GROUP BY・複合の末尾 ORDER BY に置いたら拒む。メッセージは「意図的な定数なら `Null`、並べるなら列」を勧める |
| 1b（R + D） | 記録を「MySQL では整数の `Bind` は位置になる」に改め、文書に注記する |
| 1c（ドライバー） | MySqlConnector の設定（サーバー側の prepared statement）で直るかを調べ、直るなら文書で設定を案内する |

- **推奨: 1a。**
  - 記録の約束（定数）を守れる方言の書き方は `OrderBy(Null)` で、MySQL でも定数として動くことを
    測った（Q6）。
  - `Bind(変数)` の値は解析器から見えないので、ADR 0011 の条件を満たす。
  - 1b は「同じ呼び出しの意味が方言で変わる」静かな誤りを、文書に残すだけになる。
- **決めたら要る作業**
  - MySQL レーンに twin を足す。
  - `guards-and-empty-states.md` の bound-value 段落に MySQL の例外を書く。
  - 原因（ドライバー）を確かめる。1c の結果次第で、1a の範囲（ドライバーの設定による）が変わる。

## 族 2: Oracle で整数でない数値の ORDER BY キーが列の位置になる（F2、Q3）

- **事実**: Oracle XE 21.3.0 と 23.26.3 は、`ORDER BY 2.5`・`2.0` を位置として読む（静か）。
  派生表・CTE・複合の中でも同じ。MySQL・SQLite は定数（並べない）。PostgreSQL・SQL Server は
  `Build()` が拒む。
- **記録**: guards の Bounded exception は「MySQL, SQLite and Oracle accept the no-op ordering」と
  書く。**Oracle の部分は事実として誤り**。`OrderByItemResolver` のコメントも同じ。

| 案 | 中身 |
|---|---|
| 2a（G + R） | 今ある「整数でない定数の ORDER BY」の guard に Oracle を足し、記録を直す |
| 2b（A104 + R） | Oracle の行を SQLA0104 に足し、記録を直す（`Build` は通す） |
| 2c（R のみ） | 記録を直すだけ |

- **推奨: 2a。** 同じ値について、PostgreSQL と SQL Server ではすでに guard と決めている（ADR 0011 の
  後の事例）。Oracle は拒むより悪い「別の意味」で動くので、同じ guard に入れるのが筋。
- **2a と 2b の分かれ目**: `dbms-differences.md` の「値で決まる妥当性」は、別の意味で動く値を
  SQLA0104 のセルにする道を示している（2b）。一方、この値そのものについては、guards の
  Bounded exception が「the value is invisible to the analyzer」として PostgreSQL・SQL Server を
  guard にしている。2a はその近い前例に揃える案。「ORDER BY の定数が本当に解析器から見えないか」
  （Q3）を先に決めると、両方の方言の置き場が一度に決まる。
- **付けたし（Q3）**: MySQL・SQLite の定数の扱い（並べない）は、**何もしない（E）**ことを推奨する。
  GROUP BY の非整数の定数も、MySQL・SQLite・Oracle では 1 グループとして動くだけで、報告して
  いない（`ArgumentValueValidity.FractionalGroupKeyRejected` は PostgreSQL・SQL Server だけ）。
  これと揃える。
- **決めたら要る作業**: Oracle 2 レーンの twin を「位置になる」から「拒む」に改める。guards の
  Bounded exception の文と、`OrderByItemResolver` のコメントを直す。

## 族 3: 負の ORDER BY の序数（Q2）

- **事実**: MySQL・Oracle は定数（並べない）。Oracle の複合では ORA-01785。
- **記録**: Bounded exception で決定済み。PostgreSQL・SQLite・SQL Server は拒み、MySQL・Oracle は
  通す。ただし `GroupBy(-1)` は、#684 が「読むエンジンは別の意味で読む」として全方言で拒む。
  ORDER BY との非対称の理由は書いていない。

| 案 | 中身 |
|---|---|
| 3a（A104） | MySQL・Oracle の行を足す（`Build` は今のまま） |
| 3b（G） | `GroupBy(-1)` と揃えて全方言で拒む |
| 3c（R） | 非対称は意図だと記録に書く |

- **推奨: 3a。**
  - `-1` は呼び出し側の定数で解析器から見えるので、ADR 0011 の「見えない」に当たらない（3b は
    ADR 0011 の外になる）。
  - 定数として黙って並べないのは「別の意味で実行する」なので、`dbms-differences.md` の
    値で決まる妥当性の手順（SQLA0104 のセル、意味を確かめる twin、`[!NOTE]`）に合う。
- **ただし**: 3a は、族 2 で ORDER BY の定数を「解析器から見えない」とする記録と食い違う。Q3 を
  決めるときに一緒に決める。

## 族 4: int の上限を超える整数のキー（Q17、パネル P2）

- **事実**: SQLite は `ORDER BY 2147483648` を定数、`GROUP BY 2147483648` を 1 グループとして読む
  （静か）。PostgreSQL 16 は拒む。**MySQL・Oracle・SQL Server は走らせていない。**

| 案 | 中身 |
|---|---|
| 4a | 先に残り 3 方言を測る。そのうえで、族 3 と同じ物差しで A104 にするか G にするかを決める |
| 4b（G） | 序数の guard に上限（int の範囲）を足す。どのエンジンでも列はそれほど多くないので、位置としてはどこでも無効 |

- **推奨: 4a。** 4b は「位置として無効」は普遍でも、SQLite は定数として動かす。ADR 0012 の値の域の
  条件（どの方言でも無効）に当たるかは、残り 3 方言の結果次第になる。

## 族 5: 日時の列 ± `TimeSpan`（F3）

- **事実**: SQLite と MySQL は数の足し算をする（`2026`、`20240101120000`。静か）。SQL Server は
  大きな失敗。PostgreSQL・Oracle は意図どおり。
- **記録**: なし。`docs/functions.md` は `TimeSpan` を束縛できる型として挙げるだけ。
- **補足**: C# の `TimeSpan` は定数にできない。そのため ADR 0022 の「コンパイル時の定数だけが規則に
  届く」には当たらない。ただし、MySQL と SQLite には間隔の型がないので、`TimeSpan` を束縛した
  時点で値によらず別の意味になる。つまり判断は値でなく**被演算子の静的な型**で決まる。

| 案 | 中身 |
|---|---|
| 5a（A104 を型の判断に広げる） | `+`・`-` の被演算子の静的な型が `TimeSpan` なら、MySQL・SQLite で報告する。ADR 0022 に「型だけで判断が決まる値」を足す改定が要る |
| 5b（D） | 文書に注記し、MySQL・SQLite の twin で支える。日時の足し算には `DateAdd`・`Dateadd`・`Interval` などの方言ごとの API を案内する（docs-style の「兄弟の API を指す」） |
| 5c（E） | エンジンに任せる |

- **推奨: 5a + 5b。** 解析器は誤検知なしに判断できる（型だけで決まる）。文書の注記は、解析器を
  有効にしていない利用者向けに要る。

## 族 6: 日時の列と数・日時の算術（F5 候補、Q14）

- **事実**
  - `日時 + 2`: Oracle は 2 日足す。MySQL は日時を数にして足す。SQLite は年に足す（`2026`）。
    PostgreSQL・SQL Server は失敗。
  - `日時 - 日時`: PostgreSQL・Oracle は間隔。MySQL は数の差。SQLite は 0。
- **記録**: なし。

| 案 | 中身 |
|---|---|
| 6a（A205 の拡張） | `Temporal` の列を `+`・`-` の片側に置き、もう片側が `Numeric` か `Temporal` のとき、MySQL・SQLite（と `+ 数` では Oracle）で報告する。比較だけを見ている SQLA0205 を算術に広げる |
| 6b（D） | 文書に注記し、日時の算術の API を案内する |
| 6c（E） | エンジンに任せる |

- **推奨: 6a + 6b。**
  - 区分の事実（列が日時であること）は、SQLA0205 がすでに集めている Tier 2 の事実なので、
    ADR 0010 の受け入れ条件は済んでいる。
  - 静かな誤り（MySQL・SQLite）が、型の区分だけで決まる。
- **未確認**: Oracle の `日時 + 2` は「日数を足す」が Oracle の定義どおりの意味で、呼び手によっては
  意図どおりになる。Oracle で報告するかどうかは別に決める必要がある。

## 族 7: 整数どうしの割り算（F6 候補、Q15）

- **事実**: PostgreSQL・SQLite・SQL Server は切り捨て。MySQL・Oracle は小数を返す。Oracle では、
  桁数が .NET の decimal に収まらずドライバーが失敗することもある。
- **記録**: ADR 0003 の Consequences が、切り捨てを範囲外（文書で扱う）と名指ししている。

| 案 | 中身 |
|---|---|
| 7a（E + D） | エンジンに任せると記録し、文書の割り算の節からエンジンの文書へリンクする |
| 7b（A205 の拡張） | 両辺が整数の列なら報告する。ただし `DbTypeCategory` には幅がない（意図した設計）ので、区分の設計を変える必要がある |

- **推奨: 7a。** ADR 0003 が名指しで決めている。7b は ADR 0010 の受け入れ条件（区分に幅を持ち込まない）
  とぶつかる。

## 族 8: 整数の列に小数を書く（F7 候補、Q16）

- **事実**: `2.5` を整数の列に入れると、PostgreSQL は double なら 2・decimal なら 3、SQL Server は 2、
  MySQL・Oracle は 3 になる。SQLite は 2.5 のまま保存する。
- **記録**: ADR 0003（丸め方・型の制限）。

| 案 | 中身 |
|---|---|
| 8a（E + D） | 族 7 と同じ |
| 8b（A205 の拡張） | 族 7 の 7b と同じ問題がある |

- **推奨: 8a。** 理由は族 7 と同じ。

## 族 9: 型の区分が違う比較（文字列 < 2 など）

- **事実**: MySQL は文字を数にして比べる。SQLite は型の順で比べる。PostgreSQL・SQL Server・Oracle は
  多くが失敗する。
- **記録**: SQLA0205 が決めている（メタデータがあるときだけ報告する）。

| 案 | 中身 |
|---|---|
| 9a | 今のまま |
| 9b | メタデータがなくても、定数どうしの型（列でなく、両辺が定数か束縛値）なら報告する |

- **推奨: 9a。** 9b で増えるのは、`Bind("b") < 2` のような、列を含まない比較だけ。E5 の静かな誤りは
  どれも列を含んでいて、SQLA0205 の範囲に入る。

## 族 10: MySQL の SET の評価順（F4）

- **事実**: MySQL 8.0 では、`SET b = g, g = b` の 2 つ目が、1 つ目で書いた後の値を読む。値の種類に
  よらない（E5 の 19 件すべて）。ほかの 7 レーンは更新前の値を読む。`ON DUPLICATE KEY UPDATE` の
  同じ形は、大きな失敗になる（名前が曖昧）。
- **記録**: なし。

| 案 | 中身 |
|---|---|
| 10a（解析器の新しい判断） | 同じ SET リストで、前の代入の左辺の列を後の代入の右辺が読むとき、MySQL で報告する。値でなく形の判断なので A104 には入らない。SQLA0102（文脈の規則）に入れるか、Dialect 帯の新しい ID にするかを決める必要がある（ADR 0018・0019） |
| 10b（D） | `docs/query-statements.md` の UPDATE の節に注記し、MySQL の twin で支える |
| 10c（E） | ADR 0003 の「振る舞いの違い」として、エンジンに任せる |

- **推奨: 10a + 10b。**
  - AST だけで誤検知なしに判断できる（同じ列の参照の比較）。スキーマも要らない。
  - 入れ替えの代入は、AI が書きやすい形である（ADR 0010 の使命）。
- **未確認**: MySQL の文書での根拠（単一表の UPDATE は左から評価）は、記憶にとどまり取得していない。

## 族 11: 関数の整数引数の意味（Q9）

- **対象**: SUBSTR の開始 0・負、INSTR の位置、REGEXP_* の位置・出現回数など。
- **事実**: **測っていない。**
- **記録**: 負の `Round` の桁（#742）が A104 に入った前例がある。

| 案 | 中身 |
|---|---|
| 11a | E5 と同じやり方で関数引数を測り、「別の意味で実行する」セルを A104 の行にする |
| 11b（E） | エンジン定義の意味として、文書に任せる |

- **推奨: 11a。** § 14 で型の境界に入れると決めており、前例（#742）の枠に収まる。ただし測るまで、
  族の大きさはわからない。

## 族 12: 値の位置でのドライバーの型の対応（Q10）

- **事実**
  - Oracle XE 21 は、bool の読み戻しで InvalidCastException。
  - Oracle の 2 版は、Guid で ArgumentException。
  - SQLite・MySQL の `TimeSpan`・`DateTimeOffset` は、表記がエンジンとドライバーで違う。
- **記録**: ADR 0004（値はデータとして渡す）。ドライバーの扱いについての決定はない。

| 案 | 中身 |
|---|---|
| 12a（D） | 束縛できる型の表に、方言ごとの読み戻しの注意を書き、twin で支える |
| 12b（E） | ドライバーの問題として何もしない |

- **推奨: 12a。** 失敗する組（Oracle の bool・Guid）は大きな失敗なので、急ぐものではない。表記の
  違い（静か）は、利用者が読み戻すときに初めて気づくので、文書に置く価値がある。

## 族 13: 記録だけで閉じる問い（Q5・Q6・Q8・Q13）

- **事実**: 測った結果は、どれも「大きな失敗」か「定数として意図どおり」だった。静かな誤りは F1・F2 と
  重なるものだけ。
- **推奨: E。** 族 1・2 の決定に含めて閉じ、ほかは何もしない。記録に事実を書き足すかどうかだけを
  決めればよい。

| # | 中身 | 推奨 |
|---|---|---|
| Q1 | 依頼にあった「sql-building-style.md の rule 8」は存在しない（rule 7 まで） | どの記録を指していたかを教えてほしい |
| Q7 | `OrderBy(subquery)` を拒むのは、`GroupBy(subquery)` と同じ決定か | 同じ決定として記録に書く |

## まとめ（推奨だけを並べると）

| 族 | 推奨 | 置き場 |
|---|---|---|
| 1 MySQL の `Bind(n)` キー | 拒む | G（+ ドライバーの確かめ） |
| 2 Oracle の非整数キー | 拒む、記録を直す | G + R（MySQL・SQLite は E） |
| 3 負の ORDER BY の序数 | 解析器の行 | A104 |
| 4 int の上限を超えるキー | 先に 3 方言を測る | 保留 |
| 5 日時 ± TimeSpan | 解析器（型の判断）+ 文書 | A104 の改定 + D |
| 6 日時と数・日時の算術 | スキーマの規則を算術へ + 文書 | A205 + D |
| 7 整数の割り算 | エンジンに任せる + リンク | E + D |
| 8 整数の列への小数 | エンジンに任せる + リンク | E + D |
| 9 型の違う比較 | 今のまま | — |
| 10 MySQL の SET の評価順 | 解析器の新しい判断 + 文書 | 新規 + D |
| 11 関数の整数引数 | 先に測る | 保留 |
| 12 ドライバーの型 | 文書 | D |
| 13 記録だけの問い | 何もしない | E |

推奨どおりに決めると、記録の改定が要るのは次の 4 つになる。

- ADR 0011 の事例に 2 つ（族 1・2）
- ADR 0022 の値の域に型の判断を足す（族 5）
- 新しい判断の ID の置き場（族 10）

guard を足す族（1・2）は、利用者の手元で `Build()` が新たに投げる。そのため `docs/versioning.md`
のどの区分に当たるかも、別に確かめる必要がある。

## 決定（2026-10-31、依頼者の回答）

| 族 | 決定 | 結果として決まること |
|---|---|---|
| 1 MySQL の `Bind(n)` キー | **`Build(MySql)` で拒む** | ADR 0011 の事例を 1 つ足す。ドライバーが原因かも確かめる |
| 2・3（Q3） | **記録を保ち、guard で揃える** | Oracle の非整数キーは、PostgreSQL・SQL Server と同じ `Build()` の guard に入れる。guards の Bounded exception の Oracle の文を直す。負の ORDER BY の序数は今のまま（MySQL・Oracle は通す）なので、族 3 の推奨（3a）は採らない。MySQL・SQLite の非整数（並べない）は何もしない |
| 5・6 日時の算術 | **解析器と文書の両方** | `TimeSpan` は被演算子の型で判断する（ADR 0022 を改定）。日時と数・日時は SQLA0205 を算術に広げる。どちらも文書に注記し、日時の API を案内する。Oracle の `日時 + 数` を報告するかは未決 |
